# 摘要

本报告围绕「AI 生成 PPT」这一办公高频需求，完成从工具生态调研到底层技术原理的系统研究。

核心发现：

- （1）当前市场 90% 以上的 AI PPT 工具本质上是「LLM 做内容 + 模板引擎做排版」，并非 AI 端到端设计幻灯片；
- （2）最优技术架构为 LLM → JSON → 渲染器，将创造力交给模型、正确性交给确定性代码；
- （3）底层渲染方案以 python-pptx 为主流，Aspose.Slides 为商业选择，直写 OOXML 仅用于边缘场景；
- （4）美观由设计系统、母版模板、布局引擎、AI 自检回路四层共同保证，各层均可独立编辑，不耦合于模型。

# 第一部分：AI PPT 工具全景

当前市场上的 AI PPT 工具可以按技术路线分为以下几类：

## 第一类：模板填空型（主流产品）

代表：**Gamma、Beautiful.ai、iSlide AI、讯飞智文、WPS AI、百度AI PPT**

技术流程：用户输入主题或文档 → LLM 生成大纲与分页内容 → 匹配预设模板/版式 → 将文字填入占位符 → 生成可编辑 pptx。

这类工具的核心竞争力不在模型，而在**模板的数量、质量与匹配算法**。大部分产品后端使用的是 OOXML 直写或 python-pptx 填占位符的方案。

## 第二类：全 AI 布局型

代表：**Tome、Decktopus**

做法：LLM 不仅决定内容，还决定每一页的排版方式——分几栏、图放哪、字号多大。

这种方案上限高但一致性差，容易出现"AI 风格过重"（一看就是机器做的），且可编辑性下降。目前主流趋势是收缩回模板填空型，仅保留 AI 辅助排版建议。

此外，一些对话式 PPT 生成（Chat-to-PPT），本质也是这种方案，只是逐页生成。

## 第三类：Office 内置 AI（Copilot 路线）

代表：**Microsoft 365 Copilot in PowerPoint、Google Slides Duet AI**

做法：利用 LLM 直接调用 Office 内部 API 创建原生幻灯片。优势是 100% 原生可编辑、深度集成生态；劣势是必须订阅 Microsoft 365 / Google Workspace，且定制灵活度远不如独立产品。

## 技术路线的收敛趋势

- 2022–2023：百花齐放，TOME/Gamma/各类开源方案层出不穷
- 2024：模板填空型胜出，全AI布局型退潮
- 2025+：Copilot 生态整合成为新的竞争维度

**结论**：市面绝大多数"AI PPT"工具本质上是 **LLM 做内容 + 模板引擎做排版**，并非 AI 从头设计幻灯片。真正落地的技术路线集中在模板填空型，而非端到端 AI 生成。

# 第二部分：核心技术路线

## 2.1 原生可编辑 vs 伪原生 pptx

PPTX 文件的本质是 **ZIP 压缩包，内部存储 OOXML (Office Open XML) 文件**。

|类型|XML 元素|表现|
|---|---|---|
|**真原生**|文本是 `<a:t>`（位于 `<p:sp>` 文本框内）、形状是 `<p:sp>`、图表是 `<c:chart>`、表格是 `<a:tbl>`|能选中、改字、改色、增删 ✅|
|**伪原生（图片填充）**|整页是一张 `<p:pic>` 图片|文字被"烤"进图里，改不了 ❌|
|**中间态**|SVG 当图片嵌入|也不是可编辑文字 ❌|

## 2.2 五条技术路线

| 路线 | 做法 | 优点 | 缺点 | 工程成本 | 适合 |
|---|---|---|---|---|---|
| OOXML 直写 | 代码拼 XML 再打包 | 真原生、跨平台 | 排版简陋 | 低 | 快速脚本 |
| 母版+占位符 | 设计师画版式→程序填字 | 原生+美观可控 | 版式受限 | 低–中 | 企业日常 |
| LLM→JSON→渲染器 | 模型出结构→渲染器画图 | 质量上限最高 | 工程量大 | 高 | 做产品 |
| Office 自动化 | COM/VBA/Office.js 驱动 | 100% 原生 | 需装 Office | 中 | Office 插件 |
| 商业 SDK | Aspose.Slides/Spire | 全功能跨平台 | 付费 | 中 | 全功能 |

> **「母版+占位符」vs「LLM→JSON→渲染器」辨析**：二者容易混淆，因为它们在实践中经常被组合使用，但它们是**不同层面**的东西。
>
> - **母版+占位符**是一种**渲染策略**：用 PowerPoint 模板文件（.pptx）作为"画布"，程序只负责往预留位置填文字。**设计师决定每一页长什么样**——几个占位符、放哪里、多大。
> - **LLM→JSON→渲染器**是一种**架构模式**：LLM 输出语义结构（"这是一页标题页、这是一页要点列表"），渲染器根据结构**程序化创建**幻灯片。**模型决定这一页是什么类型、有什么元素**。
>
> 打个比方来区分：
> 
> - 母版+占位符 = 设计师做了一本"填空题练习册"，程序往里填答案
> - LLM→JSON→渲染器 = 模型写了一份"菜谱"，渲染器按菜谱做菜（可以换锅换灶）
>
> **关键差异**：
> 
> - 母版+占位符路线下，LLM 输出的上限被模板锁死——模板有 5 种版式就只能出 5 种页面结构。
> - LLM→JSON→渲染器路线下，渲染器可以组合出任意布局（比如 JSON 说"这一页左文右图，下面一个表格"，渲染器按规则动态算坐标）。
>
> **【母版+占位符】是【LLM→JSON→渲染器】架构中的渲染器部分**。

## 2.3 最优架构：LLM → JSON → 渲染器

**类比**：LLM 负责写语义化大纲（这一页是什么、标题、几个要点、有一张表），渲染器相当于浏览器 + CSS 引擎，把结构"画"成真正能显示、能编辑的页面。

> 模型不该、也不需要手写底层 OOXML。

**四个角色**：

|环节|谁干|产出|关键约束|
|---|---|---|---|
|① LLM|AI|结构化 JSON|只管「想」，**不碰 OOXML**|
|② JSON 中间层|—|Schema 契约|可校验、可多模型对比、可缓存|
|③ 渲染器|确定性代码|调用 python-pptx/Aspose|只管「画」，**不决定内容**|
|④ .pptx|—|真文本/表格/图表|原生可编辑|

> 模型负责聪明，渲染器负责正确。

**为什么`LLM → JSON → 渲染器`是质量上限最高的架构**：

1. 模型不写 OOXML → 不会出格式 bug（一个标签错整份打不开）
2. 渲染前可校验（`validate()`）→ 相当于"编译检查"
3. 可多模型对比 → 不同模型输出同 schema 的 JSON，渲染器统一，横向挑最优
4. 可单页迭代 → 改一页只改那段 JSON，不推翻全部
5. 渲染与内容解耦 → 同一份 JSON，换套主题/模板就出不同风格

## 2.4 渲染器后端：四种底层操作 PPT 的方式

无论上层架构怎么设计，最终都要面对同一个问题：**如何把结构化的内容变成可编辑的 .pptx 文件**。工业界目前有四种底层方案，各有适用场景。

# 第三部分：渲染器的美观保证

## 3.1 美观的四层模型

```
美观 = 设计系统 (Design Tokens) + 母版模板 (Master) + 布局引擎 (Layout Engine) + AI 自检回路 (VLM Feedback)
           ↑ 配色字体            ↑ 版式骨架            ↑ 不溢出/对齐/一致            ↑ 自进化优化
```

| 支柱 | 做法 | 维护者 | 效果 |
|---|---|---|---|
| **设计系统** | 颜色/字体/间距/圆角固化为 token | 前端/设计 | 全局一致 |
| **母版模板** | 设计师在 PowerPoint 画好版式 | 设计师（零代码） | 最稳的"好看" |
| **布局引擎** | 网格 + 自动防溢出 + 对齐规则 | 工程师 | 不丑、不串位、不溢出 |
| **AI 自检回路** | 渲染→截图→VLM 审阅→调参→重渲染 | 模型 | 自进化 |

## 3.2 编辑渲染器的三档入口

「编辑渲染器」≠ 改 Python，而是四档递进：

| 方式 | 改什么 | 需代码 | 适合 | 灵活度 |
|---|---|---|---|---|
| ① 改 `.pptx` 母版 | 版式/占位符布局 | ❌ 零代码（PPT 可视化） | 设计师 | 版式级 |
| ② 改渲染代码 | 任意形状/逻辑 | ✅ Python | 工程师 | 无限 |
| ③ AI 闭环调优 | 让模型看截图自己改 | ❌ 对话 | 所有人 | 自动迭代 |

**方式 ① 的核心意义**：设计师在 PowerPoint「视图 → 幻灯片母版」里改占位符位置/大小/配色，渲染器代码**一行不用动**，出的 pptx 自动带上新设计。占位符是命名契约——渲染器只认 idx/type，不关心坐标。

## 3.3 文字溢出与度量

直接操作 pptx 文件时，最棘手的问题是文字超出容器边界，导致溢出或叠字。以下四种策略可按需组合：

1. **固定网格**：每页分区（标题区/正文区/图表区），内容不越界
2. **输出限长**：模型输出时约束每点字数
3. **自动缩放**：`text_frame.auto_size = MSO_AUTO_SIZE.TEXT_TO_FIT_SHAPE`
4. **约束求解布局**：布局引擎算坐标（像前端 flex/grid），质量上限最高但工程最大

# 第四部分：实战——模板处理全链路

## 4.1 模板契约检查机制

**模板的"配置"不是靠肉眼阅读的**，而是通过 python-pptx 反序列化 OOXML 后程序化抽取。检查脚本应当提取：

| 可识别内容 | 提取方式 |
|---|---|
| 母版数、版式数、版式名 | `prs.slide_masters[0].slide_layouts` |
| 每个版式的占位符（类型/索引/坐标/尺寸） | `placeholder_format.type/idx` + `Emu(sh.left).inches` |
| **占位符提示文字** ★ | `ph.has_text_frame and ph.text` — 读取版式占位符内已有的文字 |
| 主题色板（dk1/lt1/accent1–6 的 RGB） | 解压 zip → `ppt/theme/theme1.xml` → 正则抽取 `<a:srgbClr>` |
| 主题字体 | 同 theme1.xml → `<a:majorFont>/<a:minorFont>` |
| 页面尺寸 | `Emu(prs.slide_width).inches` |
| 装饰元素（图片/形状/组合及其填充色） | 遍历非占位符 shape → `shape_type/fill.fore_color.rgb` |
| 固定文字（如页码宏 `‹#›`） | `shape.has_text_frame and shape.text` |

> **★占位符提示文字的意义**：设计师在版式占位符中写入的提示（如 `"标题"`、`"时间"`、`"内容"`）是模板的**填写说明书**——它告诉渲染器或 LLM 每个坑位期望什么类型的数据。这比仅凭 `placeholder_format.type`（如 `CenteredTitle`）更精确——一个版式可能有 5 个同类型占位符，但它们的提示文字分别是 `"Q1"、"Q2"、"Q3"、"Q4"、"全年"`，LLM 就能据此生成对应的内容。读取方式与固定文字相同，但需要在**版式层面**而非幻灯片层面读取。

## 4.2 模板填充经验整理

### 1. 多母版访问

`prs.slide_layouts` 只暴露母版 #0 的版式。其他母版必须通过 `prs.slide_masters[N].slide_layouts` 访问。

```python
M0 = prs.slide_layouts                    # 母版 #0（常用：封面、目录、章节、结尾）
M1 = prs.slide_masters[1].slide_layouts   # 母版 #1（常用：内容页、分析页）
M2 = prs.slide_masters[2].slide_layouts   # 母版 #2（如果有）
```

### 2. 占位符定位策略

python-pptx 的 `list(slide.placeholders)` 按 idx 数值排序，不按视觉位置。但设计师设计模板的 idx 值常不连续（如 10→13→23），列表顺序不可靠，不能代表实际位置。

因此，推荐渲染器按如下的定位方式处理：

```python
遍历版式占位符，并记录 idx 字典 -> 根据占位符提示词所描述内容决定位置，然后使用对应占位符的 idx 字典进行填充
```

### 3.重复 idx 陷阱

设计师在设计模板时，由于复制粘贴，同一 idx 可能出现在两个不同位置。创建幻灯片时，python-pptx **只保留第一个出现的位置**，第二个被合并为同一占位符的引用副本——导致实际占位符数量少于布局声明。

**检测方法**：对比布局和幻灯片的占位符数量及位置。

**对策**：此问题无法用 python-pptx 修复，必须停止代码执行，然后让设计师进行修复。

### 4. 字体与颜色

**不要在填充脚本中设置字体、字号、颜色**。这些由设计师在母版/主题中定义，占位符写入文字后自动继承母版格式。LLM 只控制"填什么内容"，不控制"怎么显示"。

### 5.截图兜底

当出现无法判断版式布局结构时，可以请求用户截图版式，通过分析截图内容了解真实占位符的位置。

# 第五部分：结论与建议

基于对五种技术路线（2.2 节）和四种渲染后端（2.4 节）的对比分析，以下三条原则构成 AI PPT 系统设计的基石：

1. **模型不该直接输出 OOXML** —— 将创造力交给模型，将格式正确性交给渲染器。任何让 LLM 手写 XML 标签的方案都会引入不可控的格式风险。
2. **"可编辑"由渲染器保证，不由模型保证** —— 技术选型时应首先审视渲染后端（python-pptx / Aspose / Office API），而非纠结模型选型。渲染后端决定了产出的 pptx 是「真文本」还是「一张图」。
3. **美观 = 设计系统 + 母版模板 + 布局引擎 + AI 自检回路** —— 四者均可独立编辑和演进，不依赖模型能力提升。设计师通过母版改版式、工程师通过 token 调配色、模型通过 VLM 反馈做微调——各司其职。

```
│   ├── slideMasters/      # 母版（全局设计）
│   │   └── slideMaster1.xml
│   ├── slideLayouts/      # 版式（占位符布局）
│   │   └── slideLayout1.xml
│   ├── slides/            # 每一页的实际内容 ★
│   │   ├── slide1.xml
│   │   └── slide2.xml
│   ├── theme/
│   │   └── theme1.xml     # 主题配色/字体 ★
│   └── media/             # 嵌入的图片/视频
│       └── image1.png
└── docProps/              # 元数据（作者、修改时间）
```

**调试时关注的核心文件**：

- `ppt/slides/slideN.xml` — 判断是否有 `<a:t>` （真文本）还是只有 `<p:pic>`（图片填充）
- `ppt/theme/theme1.xml` — 提取色板 `<a:srgbClr>` 和字体 `<a:majorFont>`
- `ppt/slideLayouts/*.xml` — 提取占位符类型和位置
